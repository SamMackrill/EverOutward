Multiple home locations

More than one place to start.

Keep several named home locations. Choose one as current for driving distances and the next five places, while seeing every home’s own discovery circle on the map.

Feature proposal · 21 September 2026Based on the current Ever Outward code
  • Add and remove home locations
  • Exactly one current home when homes exist
  • A name, colour and map label for each home
  • One discovery circle per home; current is bolder
  • Saved driving distances for each home
  • A starting home recorded on every new visit
Same journey, different starting points.

Confirmed: all homes share one record of visited places. Each home applies the existing circle rule to that record, using its own centre and saved distances. A visit’s starting home records where that particular trip began. All existing visits will be assigned to the current home, CB3 0LL, during migration.

Interactive concept

Change the starting point. See the difference.

Make another home current, edit its name or colour, or add a location. The queue and bold circle follow the current home. Record an example visit to see the circles recalculate.

      The sketch uses a kilometre grid and simulated saved road distances, not real geography or routing. In the app, the add/edit form will use postcode search and a map pin. The numbered queue is based on saved driving distance; the circles use geographic distance.

      Product behaviour

      A small home switcher. One place to manage the details.

      On the map

      Replace the single home label with “Starting from: [name]”. Opening it lists available homes with a colour swatch, saved-distance status and a current marker. Choosing a home updates the queue, road-distance labels and circle emphasis together.

      The map keeps all non-removed home markers and circles visible. Fit to the current home and its next five by default; “Show all home locations” fits the complete set. Switching does not trigger a routing request.

      In Workspace → Home locations

      Show a clear list with Add home location, Edit, Remove and Make current. Each row shows its name, colour, current status and saved-distance count.

      The location editor requires a name and location, offers postcode lookup and map-pin adjustment, and includes a colour picker. Validate non-blank names and valid coordinates. Names need not be unique, but warn about duplicates so the switcher stays clear.

      Preserve the existing rule

      One calculation, repeated around each home.

      The active selection changes emphasis and the displayed queue. It does not determine whether another home has a circle.

      1. Find that home’s next unvisited place by road

        For home H, use only routes matching H’s ID and current location version. Order the shared set of unvisited places by saved driving distance, with the existing place-ID tie break. Keep the existing unknown-nearby-route check, including its 2 km snapping allowance, before treating the queue as confirmed.

      2. Use that next place as a geographic boundary

        Measure straight-line geographic distance from H to the next place. Then inspect all visited places from H and keep only those strictly closer than that boundary. A visit exactly on the boundary is excluded, as in the current rule.

      3. Draw to the furthest visited place inside the boundary

        The radius is the greatest of those qualifying geographic distances. A further-away visit must not enlarge the circle. Repeat independently for each home, even when that home is not current.

      Radius = furthest visited place before the next gate
      B(H) = geographic distance from H to its next unvisited place
      R(H) = max({ distance(H, V) : V is visited and distance(H, V) < B(H) } ∪ {0})

      A radius of zero means no filled area. If every catalogue place is visited, use the furthest visit from that home with no next-place boundary. If the queue is provisional or that home lacks usable distances, keep the home marker and explain why its circle is unavailable.

      Local circles use exact home coordinates. The public map should preserve the existing privacy rule: publish a rounded centre and recalculate each circle around that rounded centre, never copy the exact radius. Public queues use published visits only, so they can differ from the owner’s view.

      Data refactor

      A route belongs to a home, a location version and a place.

      Today, the journal has one settings/home record and stores routes using the place ID alone. That key would let one home overwrite another home’s distances.

      Record Proposed fields / key Responsibility
      HomeLocation id, name, colour, lat, lng, locationVersion, archivedAt, createdAt, updatedAt
      Stored as records(kind="homes", id=homeId).       		Stable identity survives renaming and moving. Increment the location version only when coordinates change. Archive instead of deleting history.
      Current selection settings/activeHomeId A single pointer, rather than a Boolean on every home. Must reference one non-archived home once setup is complete.
      Driving route homeId, homeVersion, placeId, metres, seconds, checkedAt, source, snapMetres
      Key: JSON.stringify([homeId, homeVersion, placeId]).       		Isolate every home’s route set and older location versions. Preserve manual corrections and provenance. Use metres and seconds throughout storage.
      Visit origin startingHomeId, startingHomeVersion, startingHomeSnapshot
      Snapshot: {name, colour, lat, lng}.       		Save a private snapshot of the chosen origin when the visit is saved. Home edits and current-home changes cannot rewrite a past trip.
      Per-home review report homeId, homeVersion, checkedAt, saved, total, unavailablePlaces Keep entrance-review failures and saved totals separate for every home. An agent must know which origin needs attention.

      Calculation contract

      Change refreshDrivingRoutes to take an explicit home ID and captured location version. It must not read whichever home is current between batches. A current-home switch may happen during calculation; continue for the original home. A coordinate change or removal of that home cancels further writes.

      Keep completed batches, request spacing, missing-route handling and the “saved distances do not expire” policy. Reusing a home must reuse its route set. Confirmed circle calculations can run locally with no network request.

      API and client shape

      Propose POST /api/homes, PATCH /api/homes/:id, PUT /api/homes/current and DELETE /api/homes/:id with an optional replacement ID. Validate mutations and current-home replacement atomically.

      Make route refresh explicit: POST /api/homes/:id/routes/refresh. State returns the home list, current ID, route status per home, and each home’s computed queue/range. Visit endpoints validate the starting home and snapshot it server-side.

      Public sharing needs a deliberate projection.

      Expose a trip’s starting name as a proposed public display field, never its exact snapshot coordinates or home-version internals. Home names should be friendly labels, not addresses. Keep full route records, exact locations, archived-home details and snapshots in the local backup only. The public payload can include each live home’s display name, colour, approximate circle and next-five queue, with the published current selection.

      A visitor may inspect another home’s public queue without changing the owner’s saved current home. Decide whether all home names should be public before implementation; precise locations remain private either way.

      Implementation sequence

      Keep the journal intact while adding new origins.

      1. Back up and migrate the single home

        Take a consistent SQLite backup. Add a schema-version marker and an idempotent transaction. Turn the current home, CB3 0LL, into one stable home record, use that label as the name, give it the existing green colour, retain its location version, and point activeHomeId to it.

        Re-key existing routes that match the known home version to the new composite key without recalculating them. Preserve unmatched legacy versions separately for review; do not pretend they belong to the current coordinates. Verify record counts and values before retiring the old home/route keys.

      2. Assign every existing visit to CB3 0LL

        Confirmed migration instruction: assign every existing visit, including private drafts, to the migrated CB3 0LL home. Store its stable ID, current location version and a private name/colour/coordinate snapshot as the trip origin. This is an owner-confirmed backfill, not an inference.

        Preserve visit IDs, notes, dates, people, photos, selected covers, publication flags and comments. New visits require an origin. Make the backfill idempotent: on reruns, preserve any origin already recorded or deliberately edited after migration. Verify that every pre-migration visit has an origin without changing its other fields.

      3. Refactor routing and circle calculations

        Pass explicit home identities through routing, imports, manual distance edits and exports. Calculate each home’s queue and range using its route set. Add version checks around long-running jobs and return useful per-home progress and review status.

      4. Add the home controls and visit-origin field

        Build the compact map switcher and Workspace editor. Render the labelled home layers, draw the current circle last and preserve keyboard access. Add the visit origin selector and historical display before enabling additional homes for normal use.

      5. Update publishing, backups and agent instructions

        Version the public snapshot and update the client together. Recalculate approximate circles per public home from published visits; omit private fields explicitly. Backups export all homes, active selection, route versions and visit origins. Do not refresh routes as a side effect of publishing.

        Document the proposed commands below, then exercise migration twice, restore a backup, and verify the published payload before rollout.

      Proposed agent command Purpose
      npm run homes:list List stable IDs, names, current selection, location versions and route counts without printing exact coordinates by default.
      npm run routes:refresh -- --home <id> Fill missing distances for that home’s current location. Resume batches and save a per-home review report.
      npm run routes:refresh -- --all-homes Process every non-archived home in sequence, retaining the shared routing-service rate limit.
      npm run routes:refresh -- --home <id> --force Deliberately recalculate one home’s entire set. Back up first; explain that valid returned estimates replace manual values.

      These commands and endpoints are design proposals, not implemented by this document. Existing npm run routes:refresh can remain a compatibility shortcut for the current home, resolving that home once when the run starts.

      Definition of done

      Checks that prove the feature works.

      • Create three homes; refresh the app and retain their names, colours, coordinates and exactly one current selection.
      • Store different distances to the same place from two homes. Switch repeatedly and recover each exact set without extra routing requests.
      • Show three labelled circles where their queues are confirmed. The current one is unmistakable in light/dark mode, with matching colours and with colour vision differences.
      • Use the existing strict boundary rule for each home. Test no qualifying visits, visits exactly on the boundary, out-of-order distant visits, incomplete nearby routes and an entirely visited catalogue.
      • Rename or recolour a home without invalidating routes. Move one home and invalidate only its current route version; preserve every other home and previous trip origin.
      • Switch current home while a route job runs. Results remain attached to the original home. Move/remove that original home during the job and reject further stale writes.
      • Record a trip from a non-current home. Its selected origin survives saving, editing, changing current home, moving the source home and removing that home from the active list.
      • Remove an inactive home without losing visits. Remove the current home only with an atomic replacement; prevent removal of the last home until a replacement exists.
      • Open a new visit draft, switch current home elsewhere, then save. Preserve the draft’s chosen origin or require an explicit replacement if it was removed.
      • Run migration twice without duplicate homes or routes. Verify every existing visit was assigned to CB3 0LL exactly once, preserve any later origin corrections and selected covers, and successfully restore the backup.
      • Publish a snapshot with per-home display data and approximate circles. Verify that no exact home coordinates, private origin snapshots, drafts or full route records are exposed.
      • Use the home switcher, colour editor, removal flow and visit selector on a narrow screen and with only a keyboard.

      Confirmed choices & proposed defaults

      Confirmed requirements and remaining choices.

      Choice / status Decision or proposal Why it matters
      Shared progress — confirmed One shared visited-place history; calculate every circle independently around its centre. A visit from any home counts towards every home’s circle. Starting-home attribution never splits the journey into separate challenges.
      What does “remove” mean? Archive from the map and available origins; retain referenced history and old routes. Previous visits must remain intelligible and never lose their starting location.
      Existing visit origins — confirmed Assign all existing visits to the current home, CB3 0LL. Backfill the stable home ID, location version and private origin snapshot in the migration; include drafts and preserve all other visit fields.
      Which names are public? Friendly display names and approximate circles for non-archived homes; origin names on published visits. Requires confirmation. Exact coordinates and origin snapshots remain private; names may themselves reveal a location.
